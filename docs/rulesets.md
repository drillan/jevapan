# 仕組みとルールセット

## 判定の流れ

jvp は文書を次の段階で処理する。

1. **segment**: 文書を意味的なブロックに分割する。境界は「各非空行と次の非空行」のペアを判定し、確率が閾値を超えた位置で切断する
2. **score**: 各ブロックをカテゴリごとに採点する。スコアが `threshold` 未満なら違反の可能性ありとみなす
3. **locate**: flag されたブロック内から違反している文を行レベルで特定する
4. **report**: 結果を集約し、severity に応じた終了コードを返す

採点対象から外れる領域は fenced code block、先頭の front matter、表行(`|` 始まり)の 3 種である。除外行はブロックをまたがず、行番号は原文のまま保持される。

## プリセット

`--ruleset` で選択できる同梱プリセットは 3 種ある。

| プリセット | 対象ジャンル | 構成 |
|---|---|---|
| `base` | ジャンル不問(既定) | 全ジャンル共通の 7 カテゴリ |
| `tech-doc` | 技術文書・仕様書 | base + rigor, reader_load, restraint |
| `blog` | ブログ・エッセイ | base + restraint, honesty、voice の閾値緩和 |

## 共通カテゴリ (base)

すべてのプリセットが共有する 7 カテゴリである。

| カテゴリ | スコープ | 検出するもの |
|---|---|---|
| structure | block | 話題の混在、内容を特定できない見出し |
| clarity | block | 参照先が一意に決まらない指示語、未定義の術語 |
| concision | both | 同じ主張の繰り返し、接続・評価だけの空の文 |
| voice | block | 受動態の羅列、「AI」「ツール」等への対象のぼかし |
| naturalness | block | 英語慣用句の直訳比喩、無生物の擬人化 |
| substance | block | 「重要なのは」「まとめると」等の中身のない型 |
| consistency | document | 表記・用語・文体の揺れ |

`scope: both` のカテゴリは block と document 両方で採点され、同一文への指摘は 1 件に集約される。

## 各プリセットの詳細

### base

ジャンルを問わない既定のプリセットであり、追加カテゴリを持たない。対象のジャンルが定まらない文書や、まず全体の傾向を見たい場合に適する。

### tech-doc

技術文書・仕様書向けのプリセットであり、base に 3 カテゴリを追加する。

- **rigor**: 断定の厳密さを採点する。根拠を示さない断定、「必ず解決する」式の保証、複数の要因を単一の原因へ還元する説明、機構(なぜそうなるか)を欠いた因果主張が flag される
- **reader_load**: 読者の記憶への負荷を採点する。あとで参照しない固有名(ファイル名・識別子)を持ち出す文や、概念の初出で「何の種類のものか」を示す前に性質や制約を述べる文が flag される
- **restraint**: 演出の過剰さを採点する。独立段落の決め台詞、答えを求めない修辞疑問、太字や感嘆符の多用など、説明で足りる箇所の装飾が flag される

### blog

ブログ・エッセイ向けのプリセットであり、base に 2 カテゴリを追加し、voice の閾値を緩和する。

- **honesty**: 記述の誠実さを採点する。確認していないことを確認したかのように書く文や、作為的に見える例に短い根拠も添えられていない文が flag される
- **restraint**: tech-doc と同じ基準で過剰な演出を検出する

voice の `threshold` は既定の 1.5 から 1.0 に緩和される。一人称の語りや受動態を含む文体が blog の特性であるため、通常より flag されにくくなる。

## プリセットの選び方

- 迷ったら `base` を使う。追加カテゴリが不要ならこれで足りる
- 仕様書・API ドキュメント・技術記事など、根拠と厳密さが求められる文書には `tech-doc`
- 一人称の語りや感想を含むブログ・エッセイには `blog`
- プリセットを継承してカテゴリを追加・無効化する方法は {doc}`configuration` を参照
